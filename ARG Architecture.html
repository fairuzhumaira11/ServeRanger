1Problem statement

Broken Access Control has held the #1 spot in the OWASP Top 10 since 2021, and Broken Object-Level Authorization (BOLA/IDOR) is its most common form in APIs. The defect is structurally simple — a handler fetches or modifies a record by an identifier the caller supplied, without checking that the caller is allowed to touch that specific record — yet it survives code review constantly, because the request that exploits it is syntactically identical to a legitimate one. GET /orders/502 is not malformed; it is only wrong if the caller isn't order 502's owner. No input-validation rule catches that.

Three properties of this defect class shape everything that follows:

  • It requires application semantics, not syntax. Detecting it means knowing which table a request touches, who is allowed to touch it, and whether the code actually checked that before acting.
  • It is invisible at review time and at request time alike. The code compiles; the request returns 200. Nothing looks wrong until someone specifically tests cross-account access.
  • Existing tooling detects it late, narrowly, or not at all. Our review of 17 papers on this exact problem (Section 3) found static tools that need manual authorization specs, taint scanners that answer "is there any check?" rather than "is there the right check?", and dynamic fuzzers that need a running application and a browser to even start.

The goal of this document is to specify a detection strategy that can sit inside the editor, run on code the developer hasn't committed yet, understand the authorization semantics automatically, and stay fast enough to be useful while typing — then propose the concrete architecture that implements it.

2Proposed strategy

One sentence: infer who-owns-what automatically from the ORM schema, evaluate it incrementally the way a compiler evaluates only what changed, and call a language model only when the deterministic graph genuinely cannot decide — never trusting it without independent evidence.

2.1Three borrowed ideas, one new combination

No single existing tool combines automatic authorization-model inference, incremental analysis, and disciplined LLM use. Each exists separately in the literature we reviewed; the strategy is to combine them deliberately:

IdeaWhere it comes fromHow ARG adapts it
Classify the relationship, don't just trace taint BolaRay (CCS'24) infers four object-level authorization models — Ownership, Membership, Hierarchical, Status — from database foreign keys. Read the same relationships straight from ORM annotations (@ManyToOne, @JoinColumn, belongs_to, ForeignKey()) instead of reverse-engineering them from raw SQL text — skipping BolaRay's hardest step entirely.
Analyze on demand, not the whole program Zipper (USENIX Sec'25) caches a symbolic summary per function and only re-derives what a change could affect, instead of eagerly analyzing every path. Cache one ARG summary per function, keyed by an AST-subtree hash; an edit invalidates only that function and its direct callers/callees.
Let the model propose, never decide IRIS (ICLR'25) has an LLM guess taint specs, a deterministic engine test them against real code paths, and the LLM re-verify only concrete candidates with context. An LLM may propose which field is the owner ID or which helper method is an authorization check; a deterministic pass must find AST/dataflow evidence for that guess before it is ever shown as anything more than "needs review."

2.2What "solving the issue better" means here

Concretely, the strategy is designed to answer a sharper question than prior tools ask. A generic taint scanner asks: is there any authorization check on this path? ARG asks: is there the check this specific relationship requires? A post-login page that checks a role but not object ownership passes the first question and correctly fails the second — which is exactly the shape of the CVE-class bugs cited throughout Section 3.

3.1The four reasons, stated plainly

  • Precision beyond taint tracking. BolaRay's own evaluation found zero false negatives against 15 known CVEs precisely because it checks for the correct relationship-specific guard, not merely "a guard exists." A generic taint scanner cannot express that distinction; ARG is built around it from the start.
  • No manual specification burden. BolaRay still requires ~13 lines of hand-written Data Access Layer specification per framework API it doesn't recognize — "a one-time effort... considered a barrier to adopting the tool," in the authors' own words. ARG removes that barrier for any ORM that declares relationships as annotations, which covers the large majority of modern backend frameworks.
  • Speed that matches the tool's location. A tool that takes 30 seconds to 7 minutes per application (BolaRay, YASA, Zipper) is a CI-stage tool. Placing the same class of analysis inside an editor requires Zipper's on-demand, per-function caching discipline applied specifically to the authorization-model problem — which no existing BOLA-specific tool does.
  • A finding that becomes enforcement. Every academic tool reviewed stops at a report. ARG emits the same manifest format your own Zero Trace plan already designs a runtime guard around, so a finding in the editor, a failed CI check, and a blocked production request can all cite the same rule ID.
Net effect

ARG is not a new detection algorithm competing with BolaRay, YASA, or IRIS — it is the specific combination of their individually-solved sub-problems (model inference, incremental speed, guarded LLM use) that none of them combine, applied to the one vulnerability class where combining them matters most.

5The ARG decision engine

This is the algorithm inside the dashed box in Figure 1 — the actual research contribution. It is a direct adaptation of BolaRay's four inference rules, reading schema from ORM annotations instead of reconstructing it from SQL text, with an explicit escape hatch for cases it can't resolve alone.

5.1Worked example

@GetMapping("/api/orders/{id}")
public Order getOrder(@PathVariable Long id) {
    return orderRepository.findById(id);   // Step 1: sensitive op on Order
}

// Schema (Step 1):      Order.ownerId -> User.id
// Classification (Step 2): Ownership model
// Verify (Steps 3-4):   no predicate binds Order.ownerId to session userId
// Result:               CONFIRMED: POTENTIAL_BOLA

This is the same shape as the CVE-class bugs BolaRay reported 178 new instances of: a role or authentication check may well be present elsewhere in the method, but the object-level check — does this user own this order — is what's missing, and it is the only question this defect class actually turns on.

7Working methodology — full walkthrough

Tracing one function from keystroke to production enforcement, through every diagram above, end to end.

1 · Developer writes the handler
A controller method is added: GET /api/orders/{id}, calling orderRepository.findById(id). No ownership check is present.
2 · Editor sends the AST subtree (Figure 1, top)
On save (MVP) or on keystroke (post-MVP), the LSP client sends only the changed function's parsed subtree to the ARG engine.
3 · Schema Builder reads the entity (Figure 1 / Figure 2, Step 1)
The Order entity's @ManyToOne User owner annotation is read directly — no SQL reverse-engineering required.
4 · Model Classifier labels the relationship (Figure 2, Step 2)
A 1:n relationship from the user table is classified Ownership.
5 · Guard Verifier checks the call (Figure 2, Steps 3–4)
No predicate in getOrder compares Order.ownerId to the authenticated userId. The deterministic path concludes CONFIRMED: POTENTIAL_BOLA directly — Guarded Inference isn't even needed for a case this clear-cut.
6 · Fast lane shows the diagnostic (Figure 3, top lane)
Under 300 ms after the save, the IDE shows a squiggle under orderRepository.findById(id) with a quick fix: "Insert ownership check."
7 · Manifest entry is written (Figure 1, center)
The same finding is appended to zerotrace-policy.json with a rule ID, the entity, the required model, and the confidence tier (CONFIRMED).
8 · CI gate blocks the pull request (Figure 1, bottom-center)
If the developer pushes anyway, zerotrace check --fail-on=CONFIRMED reads the same manifest entry and fails the build before merge.
9 · Runtime guard enforces it in production (Figure 1, bottom-right)
If the code ships regardless, the Layer 2 interposer loads the same manifest, sees the Ownership rule for this endpoint, and returns 403 the first time a request's owner ID doesn't match the session's user ID — independent of the static analysis having ever run against that exact deployed binary.
Why the walkthrough matters

Every step above cites the same rule ID. That traceability — one inference, three enforcement points — is the concrete, demonstrable version of "the runtime policy was generated from development-time source-code analysis," which your own Zero Trace plan names as the strongest possible demonstration of the whole project.

9Risks & mitigations

False positives
Over-eager "every relationship needs a check"
BolaRay's own evaluation reported a 21.86% false-positive rate, mostly from application-level roles it couldn't see.
Confidence tiers in the UI; scope v1 to write operations, as BolaRay itself does.
Coverage
Every ORM needs its own frontend
A JPA frontend contributes nothing to a Django or Prisma codebase.
Keep the shared IR narrow (entity, relationship, repo-call, guard) so new frontends are additive.
Performance
Realtime is the hardest claim here
Existing tools in this space report 30 s to 7 min per run.
Function-scoped caching (Figure 3); full rebuild stays a save/CI-time operation.
LLM trust
A confident, wrong LLM guess
An invented owner-field mapping is worse than no suggestion.
Guarded Inference never flips a finding alone (Figure 2); always badged distinctly.

10Conclusion

ARG is not a claim that any individual idea in this document is novel — BolaRay's model taxonomy, Zipper's on-demand analysis, and IRIS's guarded LLM loop are each published, evaluated work. The proposal is that combining them, specifically for the authorization-relationship problem and specifically inside an editor, closes a gap that is visible across all 17 papers reviewed but closed by none of them: a tool that infers authorization semantics automatically, runs fast enough to be live, uses a language model without trusting it blindly, and produces one artifact that an IDE, a CI pipeline, and a production guard can all act on identically.
